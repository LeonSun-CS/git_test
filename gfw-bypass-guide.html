2. Understanding the Great Firewall

2.1 How the GFW Works (2024/2025)

The Great Firewall employs multiple sophisticated detection and blocking mechanisms:

DNS Manipulation

DNS queries for blocked domains return false IP addresses or no response. This is the first line of defense.

IP Blocking

Direct blocking of IP addresses associated with VPN providers, proxy servers, and circumvention tools. IP blocks can last from hours to permanent.

Deep Packet Inspection (DPI)

The GFW analyzes:

  • Packet Headers: Protocol signatures, port numbers, packet sizes
  • Payload Content: Pattern matching for known VPN protocols
  • Traffic Entropy: Encrypted traffic has high entropy; the GFW uses statistical analysis
  • Timing Patterns: Connection timing and packet interval analysis
  • TLS Fingerprints: ClientHello messages, cipher suites, extensions order

Active Probing (Critical Understanding)

When the GFW suspects a server is running circumvention software:

  1. Passive Detection: Traffic patterns trigger suspicion (e.g., high entropy, specific packet sizes)
  2. Active Testing: The GFW sends probe packets from Chinese IP addresses to test the server
  3. Confirmation: If the server responds in expected ways, it confirms the protocol
  4. Blocking: The IP is added to blocklists (can be temporary or permanent)
Critical Finding (November 2021 - Present): The GFW can detect and block fully encrypted traffic in real-time using heuristics that exempt unlikely encrypted traffic, then block the rest based on protocol fingerprints, bit patterns, and ASCII character analysis.

QUIC Protocol Detection (Since April 2024)

New Discovery: Since April 7, 2024, the GFW can decrypt QUIC Initial packets at scale. The encryption key can be derived from publicly visible data (Destination Connection ID + version-specific salt), allowing SNI inspection. However, the GFW cannot reassemble QUIC packets split across multiple UDP datagrams - a weakness that can be exploited.

Regional Variations

Recent research (2024-2025) discovered that some provinces implement additional censorship beyond the GFW:

  • Henan Firewall: Blocks 4.2 million domains (5x more than GFW)
  • More aggressive and volatile blocking policies
  • Variations by ISP (China Telecom, China Unicom, China Mobile)

2.2 What Gets You Detected

Common Mistakes Leading to Detection:
  • Using default configurations without obfuscation
  • Choosing cloud providers already known to host VPNs (AWS, GCP, DigitalOcean)
  • Using standard VPN ports (1194 for OpenVPN, 500/4500 for IPsec)
  • Not using TLS or using self-signed certificates incorrectly
  • Running services that respond to unauthenticated probes
  • Poor password choices for Shadowsocks (enabling brute-force probing)
  • Using old protocol versions (Shadowsocks without AEAD ciphers)
  • Not implementing replay protection
  • Running on residential IPs that suddenly exhibit server-like behavior

4. Detailed Protocol Setup Guides

4.1 Xray-core with REALITY Protocol (Recommended)

Best for: Home server setup, maximum stealth, no domain name required

Overview

REALITY (introduced in Xray-core v1.8.0) implements full TLS using the SNI of a legitimate camouflage website. This eliminates your server's TLS fingerprint while maintaining perfect forward secrecy.

Key Advantages

  • No domain name or DNS records required
  • No need to manage TLS certificates
  • "Steals" TLS from legitimate websites (e.g., microsoft.com, addons.mozilla.org)
  • To GFW, traffic appears identical to accessing the legitimate site
  • Requires Xray-core 1.8.0+ on both client and server

Installation Steps

1. Install Xray-core on your home server:

bash -c "$(curl -L https://github.com/XTLS/Xray-install/raw/main/install-release.sh)" @ install

2. Generate UUID and keys:

# Generate client UUID
/usr/local/bin/xray uuid

# Generate REALITY key pair
/usr/local/bin/xray x25519

Save the output - you'll need:

  • UUID (for client authentication)
  • Private key (for server config)
  • Public key (for client config)

3. Configure Server (/usr/local/etc/xray/config.json):

{
  "log": {
    "loglevel": "warning"
  },
  "inbounds": [
    {
      "port": 443,
      "protocol": "vless",
      "settings": {
        "clients": [
          {
            "id": "YOUR_UUID_HERE",
            "flow": "xtls-rprx-vision"
          }
        ],
        "decryption": "none"
      },
      "streamSettings": {
        "network": "tcp",
        "security": "reality",
        "realitySettings": {
          "show": false,
          "dest": "microsoft.com:443",
          "xver": 0,
          "serverNames": [
            "microsoft.com",
            "www.microsoft.com"
          ],
          "privateKey": "YOUR_PRIVATE_KEY_HERE",
          "shortIds": [
            "",
            "0123456789abcdef"
          ]
        }
      }
    }
  ],
  "outbounds": [
    {
      "protocol": "freedom",
      "tag": "direct"
    }
  ]
}

Key Configuration Notes:

  • port: 443 - Use standard HTTPS port
  • flow: "xtls-rprx-vision" - Solves TLS-in-TLS detection
  • dest: "microsoft.com:443" - Target website (must support TLS 1.3 and H2)
  • serverNames - Domains to mimic (should match dest)
  • Choose popular websites with TLS 1.3: microsoft.com, addons.mozilla.org, www.lovelive-anime.jp

4. Start and enable Xray:

systemctl start xray
systemctl enable xray
systemctl status xray

5. Configure Firewall (if using UFW):

ufw allow 443/tcp
ufw reload

Client config (for v2rayN, NekoBox, etc.):

    {
      "protocol": "vless",
      "settings": {
        "vnext": [
          {

4.2 V2Ray/VMess with WebSocket + TLS + Nginx

Best for: Users who already have a domain name and want a proven solution

Architecture

Client → HTTPS (443) → Nginx → WebSocket → V2Ray Server → Internet
                                              ↓
                              Appears as normal HTTPS website traffic

Requirements

  • Domain name pointing to your server IP
  • Let's Encrypt SSL certificate (free, automatic)
  • Nginx or Caddy as reverse proxy

Installation Steps

1. Install V2Ray:

bash <(curl -L https://raw.githubusercontent.com/v2fly/fhs-install-v2ray/master/install-release.sh)

2. Install Nginx and Certbot:

apt update && apt install -y nginx certbot python3-certbot-nginx

3. Get SSL Certificate:

certbot --nginx -d yourdomain.com

4. Configure V2Ray (/usr/local/etc/v2ray/config.json):

{
  "inbounds": [
    {
      "port": 10000,
      "listen": "127.0.0.1",
      "protocol": "vmess",
      "settings": {
        "clients": [
          {
            "id": "YOUR_UUID_HERE",
            "alterId": 0
          }
        ]
      },
      "streamSettings": {
        "network": "ws",
        "wsSettings": {
          "path": "/your-secret-path"
        }
      }
    }
  ],
  "outbounds": [
    {
      "protocol": "freedom"
    }
  ]
}

5. Configure Nginx:

server {
    listen 443 ssl http2;
    server_name yourdomain.com;

    ssl_certificate /etc/letsencrypt/live/yourdomain.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/yourdomain.com/privkey.pem;
    ssl_protocols TLSv1.2 TLSv1.3;
    ssl_ciphers HIGH:!aNULL:!MD5;

    # Serve a fake website
    location / {
        root /var/www/html;
        index index.html;
    }

    # Proxy V2Ray WebSocket
    location /your-secret-path {
        proxy_redirect off;
        proxy_pass http://127.0.0.1:10000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}

6. Create a simple decoy website:

echo "<html><body><h1>Welcome</h1></body></html>" > /var/www/html/index.html

7. Start services:

systemctl restart v2ray nginx
systemctl enable v2ray nginx

Upgrade to VLESS+XTLS+Vision

Important: VMess has TLS-in-TLS detection issues. Upgrade to VLESS+XTLS+Vision for better stealth.

Change protocol to "vless" and add flow setting as shown in the REALITY example above.

4.3 Trojan-GFW Protocol

Best for: Users who want simplicity with good stealth, have a domain name

How It Works

Trojan disguises proxy traffic as standard HTTPS traffic. Failed authentication attempts return a legitimate website, making active probing ineffective.

Installation

1. Install Trojan:

# Download latest release
wget https://github.com/trojan-gfw/trojan/releases/download/v1.16.0/trojan-1.16.0-linux-amd64.tar.xz
tar -xvf trojan-1.16.0-linux-amd64.tar.xz
cd trojan
sudo cp trojan /usr/local/bin/

2. Get SSL Certificate:

certbot certonly --standalone -d yourdomain.com

3. Configure Trojan (/etc/trojan/config.json):

{
    "run_type": "server",
    "local_addr": "0.0.0.0",
    "local_port": 443,
    "remote_addr": "127.0.0.1",
    "remote_port": 80,
    "password": [
        "your_strong_password_here"
    ],
    "ssl": {
        "cert": "/etc/letsencrypt/live/yourdomain.com/fullchain.pem",
        "key": "/etc/letsencrypt/live/yourdomain.com/privkey.pem",
        "sni": "yourdomain.com"
    }
}

4. Create systemd service:

# /etc/systemd/system/trojan.service
[Unit]
Description=Trojan
After=network.target

[Service]
Type=simple
ExecStart=/usr/local/bin/trojan /etc/trojan/config.json
Restart=on-failure

[Install]
WantedBy=multi-user.target

5. Start Trojan:

systemctl daemon-reload
systemctl start trojan
systemctl enable trojan
Security Note: Trojan has not undergone formal security auditing. Use with caution and keep updated.

4.4 NaiveProxy with Caddy

Best for: Maximum TLS fingerprint resistance, advanced users

Why NaiveProxy

  • Uses Chromium's network stack - identical to Chrome browser traffic
  • Immune to TLS fingerprinting
  • During 2021 blocking wave, no reports of NaiveProxy blocks

Installation

1. Build Caddy with ForwardProxy:

# Install Go
wget https://go.dev/dl/go1.21.0.linux-amd64.tar.gz
sudo tar -C /usr/local -xzf go1.21.0.linux-amd64.tar.gz
export PATH=$PATH:/usr/local/go/bin

# Install xcaddy
go install github.com/caddyserver/xcaddy/cmd/xcaddy@latest

# Build Caddy with NaiveProxy's forwardproxy
~/go/bin/xcaddy build --with github.com/caddyserver/forwardproxy=github.com/klzgrad/forwardproxy@naive

# Move to system
sudo mv caddy /usr/local/bin/

2. Create Caddyfile (/etc/caddy/Caddyfile):

{
    order forward_proxy before file_server
}

:443, yourdomain.com {
    tls your-email@example.com

    forward_proxy {
        basic_auth user your_strong_password
        hide_ip
        hide_via
        probe_resistance
    }

    file_server {
        root /var/www/html
    }
}

3. Create systemd service and start:

sudo systemctl enable caddy
sudo systemctl start caddy

Client Setup

NaiveProxy client config.json:

{
  "listen": "socks://127.0.0.1:1080",
  "proxy": "https://user:your_strong_password@yourdomain.com"
}

4.5 Shadowsocks (Use with Extreme Caution)

⚠️ Warning: Shadowsocks is actively being detected and blocked by the GFW. Only use with proper configuration and expect frequent IP changes. Not recommended as primary solution.

If You Must Use Shadowsocks

1. Install Shadowsocks-libev (v3.3.1+):

apt install shadowsocks-libev

2. CRITICAL Configuration (/etc/shadowsocks-libev/config.json):

{
    "server": "0.0.0.0",
    "server_port": 8388,
    "password": "MUST_BE_LONG_RANDOM_USE_COMMAND_BELOW",
    "timeout": 300,
    "method": "chacha20-ietf-poly1305",
    "mode": "tcp_and_udp"
}

3. Generate strong password:

openssl rand -base64 16

4. Add obfuscation plugin (REQUIRED):

{
    "server": "0.0.0.0",
    "server_port": 443,
    "password": "YOUR_STRONG_RANDOM_PASSWORD",
    "timeout": 300,
    "method": "chacha20-ietf-poly1305",
    "mode": "tcp_and_udp",
    "plugin": "v2ray-plugin",
    "plugin_opts": "server;tls;host=yourdomain.com;cert=/path/to/cert.pem;key=/path/to/key.pem"
}

Required Protections

✓ MUST USE:
  • Shadowsocks-libev v3.3.1 or newer
  • AEAD ciphers only (chacha20-ietf-poly1305, aes-256-gcm)
  • Long random password (minimum 16 characters)
  • Obfuscation plugin (v2ray-plugin or simple-obfs)
  • Non-standard port or port 443 with TLS
  • Consider changing packet sizes (mitigates active probing)
Better Alternative: Use Shadowsocks through sing-box or as a fallback protocol in a multi-protocol setup with V2Ray/Xray.

6. Security & Anti-Detection Best Practices

6.1 Defending Against Active Probing

Critical Understanding: The GFW actively tests suspected servers. Your server must resist these probes.

How GFW Active Probing Works

  1. Passive Detection: Traffic patterns trigger suspicion
  2. Probe Launch: GFW sends test packets from Chinese IPs
  3. Response Analysis: Server responses reveal protocol
  4. Blocking Decision: IP gets blocked if confirmed

Defense Strategies

1. Authentication Before Response:

  • Never respond to unauthenticated requests with protocol-specific data
  • Trojan: Returns normal HTTPS content on bad password
  • REALITY: Appears as legitimate website
  • Shadowsocks: Use strong password + AEAD

2. Whitelist Firewall Strategy:

# Allow only known client IPs (if possible)
ufw allow from CLIENT_IP to any port 443

# Or use port knocking
# Install knockd
apt install knockd

# Configure knock sequence in /etc/knockd.conf
[openSSH]
sequence = 7000,8000,9000
seq_timeout = 5
command = /sbin/iptables -A INPUT -s %IP% -p tcp --dport 443 -j ACCEPT

3. Implement "Read Forever" Strategy:

  • On invalid handshake, keep connection open without responding
  • Forces probing system to timeout
  • Implemented in latest Shadowsocks-libev, Outline

4. Use Non-Standard Configurations:

  • Avoid default ports, paths, and UUIDs
  • Change WebSocket paths regularly
  • Use random, long passwords/UUIDs

6.2 TLS Fingerprinting Avoidance

The Problem

TLS ClientHello messages contain identifiable patterns:

  • Cipher suite order
  • Extension order and values
  • TLS version preferences
  • Curve preferences

Solutions

1. Use REALITY (Best):

  • Eliminates server-side TLS fingerprint entirely
  • Mimics legitimate websites' TLS signatures

2. Use uTLS (Mimic Browser):

  • Xray/V2Ray with uTLS support
  • Fingerprint appears as Chrome, Firefox, Safari, etc.
  • Set in client config: "fingerprint": "chrome"

3. Use NaiveProxy:

  • Actually uses Chrome's network stack
  • Impossible to distinguish from real Chrome

6.3 Traffic Pattern Obfuscation

Timing Obfuscation

# Xray config - add random padding
"streamSettings": {
    "sockopt": {
        "tcpFastOpen": true,
        "tproxy": "off"
    }
}

Packet Size Randomization

For Shadowsocks:

  • Use plugin to modify packet sizes
  • Prevents entropy-based detection

Protocol Multiplexing

Run multiple protocols on same server:

  • Trojan on port 443
  • Shadowsocks on different port as backup
  • Fall back if one gets detected

6.4 Server Hosting Best Practices

Residential ISP (Your Home - Spectrum)

Advantages:

  • ✓ Less likely to be on VPN provider blocklists
  • ✓ Trusted IP reputation
  • ✓ Free hosting (just your home internet)
  • ✓ Full control over hardware

Disadvantages:

  • ✗ Slower upload speeds
  • ✗ Dynamic IP (solved with DDNS)
  • ✗ May have port restrictions
  • ✗ Your IP exposed (consider risk)

Mitigation:

  • Use DDNS for dynamic IP
  • Use REALITY (no domain needed)
  • Monitor for unusual activity
  • Set bandwidth limits if needed

If Using VPS (Alternative)

Recommended Providers (GFW Resistant):

  • Avoid: AWS, Google Cloud, DigitalOcean (commonly blocked)
  • Consider: Smaller providers, CN2 GIA routes
  • Best: Residential ISP (your home) or lesser-known data centers

Server Location:

  • West Coast USA (lower latency to China)
  • Hong Kong (fast but heavily monitored)
  • Japan, South Korea (good balance)
  • Europe (higher latency but diverse routing)

6.5 OPSEC (Operational Security)

Important Considerations:
  • Don't discuss details publicly: Avoid posting your server IP, domain, or config details on public forums
  • Limit sharing: Only share connection details with trusted users
  • Monitor access logs: Watch for unusual connection attempts
  • Change configs periodically: Update UUIDs, paths, passwords every few months
  • Have backup plan: Run multiple protocols or have backup server
  • Test regularly: Have your friend test connection stability

8. Troubleshooting

8.1 Connection Issues

Problem: Can't Connect at All

Diagnose:

# On server - check if service is running
systemctl status xray
journalctl -u xray -n 50

# Check if port is listening
netstat -tulpn | grep 443
# or
ss -tulpn | grep 443

# Check firewall
ufw status
iptables -L -n

# From client - test connectivity
ping YOUR_SERVER_IP
telnet YOUR_SERVER_IP 443
# or
nc -zv YOUR_SERVER_IP 443

Solutions:

  • Verify port forwarding on router
  • Check server firewall allows port 443
  • Verify Xray/V2Ray is running
  • Check client config matches server (UUID, port, protocol)
  • Verify Dynamic DNS is updated with current IP

Problem: Connects But No Internet

Diagnose:

# Check server logs for errors
tail -f /var/log/xray/error.log

# Test server's outbound connection
curl -I https://www.google.com

Solutions:

  • Check server routing and DNS settings
  • Verify outbound rules in config.json
  • Ensure server has internet access
  • Check client routing settings

Problem: Connection Drops Frequently

Possible Causes:

  • ISP connection instability
  • GFW active probing (server getting blocked temporarily)
  • Resource exhaustion on server
  • Keep-alive timeout issues

Solutions:

# Increase timeout values in config.json
"policy": {
    "levels": {
        "0": {
            "connIdle": 300,
            "handshake": 4
        }
    }
}

# Enable TCP Fast Open
"streamSettings": {
    "sockopt": {
        "tcpFastOpen": true,
        "tcpKeepAliveInterval": 30
    }
}

# Check server resources
htop
df -h
free -h

8.2 Performance Issues

Problem: Slow Speeds

Diagnose:

# Test server's actual bandwidth
# Install speedtest-cli
pip3 install speedtest-cli
speedtest-cli

# Check CPU usage during transfer
htop

# Monitor network I/O
iftop  # apt install iftop

Solutions:

  • Enable BBR congestion control (see section 6.6)
  • Use XTLS instead of TLS (reduces encryption overhead)
  • Optimize buffer sizes in config
  • Check for bandwidth throttling by Spectrum
  • Consider upgrading home internet plan (especially upload speed)
  • Switch to lighter protocol (VLESS vs VMess)

Problem: High Latency

Expected latency USA-China: 150-250ms

If higher:

  • Use mtr to trace route: mtr -r -c 100 google.com
  • Check for packet loss
  • Consider using UDP-based protocols (QUIC/Hysteria)
  • Optimize routing (may require changing ISP or using VPS)

8.3 Detection and Blocking

Problem: Worked Yesterday, Blocked Today

Likely cause: GFW detected and temporarily blocked your IP/protocol

Immediate actions:

  1. Wait: Many blocks are temporary (1 hour to 1 day)
  2. Check logs: Look for unusual connection attempts (GFW probes)
  3. Verify IP: Has your Dynamic IP changed? Update DDNS
  4. Switch protocol: If running multiple protocols, try another

Long-term solutions:

  • Switch to REALITY (hardest to detect)
  • Implement active probing defenses (section 6.1)
  • Use authentication before any response
  • Consider changing server config/ports
  • Monitor for GFW probe patterns in logs

Problem: Shadowsocks Keeps Getting Blocked

This is expected behavior in 2024/2025

Options:

  • Switch to V2Ray/Xray with REALITY
  • Use Shadowsocks with obfuscation plugin
  • Change server IP frequently
  • Implement packet size randomization
  • Use as backup only, not primary

Solution:

# Check current IP
curl ifconfig.me

Problem: Port Forwarding Not Working

Diagnose:

# From another network (use phone data or ask friend):
telnet YOUR_PUBLIC_IP 443

# From inside network:
# Check server is listening
netstat -tulpn | grep 443

# Use online port checker:
# https://www.yougetsignal.com/tools/open-ports/

Solutions:

  • Verify router port forwarding rule
  • Check if ISP blocks port 443 (call Spectrum)
  • Try different port (8443, 2053) and update config
  • Disable router firewall temporarily to test
  • Check for double NAT (router behind another router)

8.5 Certificate Issues (TLS-based Protocols)

Problem: TLS Certificate Expired

# Check certificate expiry
echo | openssl s_client -servername yourdomain.com -connect localhost:443 2>/dev/null | openssl x509 -noout -dates

# Renew Let's Encrypt certificate
certbot renew

# Or force renewal
certbot renew --force-renewal

# Verify auto-renewal is set up
systemctl list-timers | grep certbot

# Test renewal process
certbot renew --dry-run

Problem: Certificate Can't Be Obtained

Common causes:

  • Domain not pointing to correct IP
  • Port 80 blocked (needed for HTTP challenge)
  • Firewall blocking Certbot

Solutions:

# Use DNS challenge instead of HTTP
certbot certonly --manual --preferred-challenges dns -d yourdomain.com

# Or use standalone mode (stop web server first)
systemctl stop nginx
certbot certonly --standalone -d yourdomain.com
systemctl start nginx

8.6 Client-Side Troubleshooting

Problem: Client Can't Import Config

Solutions:

  • Verify JSON syntax: cat config.json | jq .
  • Check config format matches client expectations
  • Try different import method (JSON vs share link)
  • Update client to latest version
  • Check share link encoding (base64 issues)

Problem: "Bad Configuration" Error

Common mistakes:

  • UUID mismatch between client and server
  • Wrong protocol specified
  • Port number incorrect
  • Security/encryption settings mismatch
  • Missing required fields (flow, fingerprint, etc.)

Validation:

# Server-side - validate config
xray run -test -c /usr/local/etc/xray/config.json

# Should output: "Configuration OK"

8.7 Emergency Fallback Plan

Always Have a Backup:
  • Run multiple protocols simultaneously (Xray + Shadowsocks)
  • Have configs for different ports
  • Keep a VPS as backup server
  • Share configs through secure channel (encrypted message)
  • Document setup so you can rebuild quickly
  • Test backup methods monthly

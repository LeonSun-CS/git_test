Understanding the Great Firewall (GFW)

Detection Methods (2024-2025 Updates)

1. Deep Packet Inspection (DPI)

The GFW analyzes both headers and payloads of data packets, identifying traffic patterns specific to protocols. As of November 2021, the GFW deployed advanced censorship that passively detects and blocks fully encrypted traffic in real-time.

Detection Heuristics: The GFW applies crude but efficient heuristics based on:
  • Fingerprints of common protocols
  • Fraction of set bits in packets
  • Number, fraction, and position of printable ASCII characters
  • Packet size and entropy of first data packet

2. Active Probing

When the GFW detects suspicious traffic, it sends active probes to the server to confirm it's a circumvention tool. On average, probes arrive within half a second of detecting potential proxy traffic.

  • Replay-based probes: Replays captured traffic to test server response
  • Random probes: Sends crafted packets with varied lengths
  • TLS probing: Attempts TLS handshakes to detect proxy servers

3. QUIC/SNI-based Censorship (New 2024)

Starting April 7, 2024, the GFW began blocking QUIC connections to specific domains by decrypting QUIC Initial packets at scale using cryptographic analysis.

4. TLS Fingerprinting

The GFW analyzes TLS handshakes to identify:

  • Cipher suites and their order
  • TLS extensions
  • TLS version field
  • Server Name Indication (SNI) - even encrypted SNI (ESNI) is now blocked
  • "TLS-in-TLS" patterns (double encryption) that indicate proxy usage

5. Traffic Pattern Analysis

The GFW examines timing patterns, packet sizes, and connection characteristics to identify VPN traffic even when encrypted.

6. Regional Censorship Layers

Research in 2025 revealed "A Wall Behind A Wall" - regional firewalls (like Henan Firewall) that employ more aggressive blocking than the national GFW, blocking 5x more domains.

August 2025 Port 443 Incident: On August 20, 2025, the GFW exhibited anomalous behavior by unconditionally disrupting ALL connections on TCP port 443 for over an hour, causing massive internet disruption. This demonstrates the GFW's capability for large-scale interference.

IP Blocking Patterns

The GFW strategically limits blocking to specific IP ranges of popular datacenters, applying probabilistic blocking to 26% of connections. Datacenter IPs experience 30-50% blocking rates, while residential IPs have 99% lower detection rates.

IPv6 Considerations

Opportunity: IPv6 currently has less stringent blocking than IPv4. CERNET (academic network) users can access blocked websites via IPv6. However, DNS infrastructure still runs over IPv4, so DNS-based blocking still applies.

CDN Integration & Domain Fronting

Cloudflare WebSocket Configuration

Cloudflare's CDN can add an extra layer of obfuscation by routing traffic through their global network, making it harder for the GFW to identify and block your server.

How it Works: Client connects via WebSocket to Cloudflare CDN, which forwards to Caddy reverse proxy, which connects to your Xray/V2Ray server. The GFW sees only Cloudflare IPs and HTTPS traffic.

Advantages:

  • Your server IP is hidden behind Cloudflare
  • Traffic appears as regular HTTPS to Cloudflare
  • Global CDN provides acceleration
  • Free tier available
  • SSL/TLS handled automatically

Configuration Steps:

  1. Register domain with Cloudflare DNS
  2. Enable "Proxied" (orange cloud) for DNS record
  3. Configure V2Ray/Xray with WebSocket transport
  4. Set up Caddy/Nginx as reverse proxy
  5. Enable TLS in Cloudflare (Full or Full Strict mode)

Domain Fronting (Advanced)

Status: Domain fronting has been restricted by major CDN providers (AWS, Google, Microsoft) since 2018. However, it remains feasible with 22 out of 30 tested CDNs including Akamai and Fastly.

How Domain Fronting Works: A mismatch between the SNI extension (visible domain) and the HTTP Host header (covert domain). The GFW sees connection to allowed domain, but actual traffic goes to blocked domain.

Why Censors Can't Block It:

Blocking the front domain would cause massive collateral damage. When Russia tried blocking Telegram's domain fronting in 2018, they blocked 15.8 million IPs belonging to Google and Amazon CDNs, causing outages for banks, retailers, and major websites.

Current Limitations:

  • Major providers (Cloudflare, AWS CloudFront, Azure, GCP) block domain fronting
  • Requires finding CDN that still allows it
  • Complex to set up and maintain
  • May be detected by advanced DPI

# Update system
sudo apt update && sudo apt upgrade -y

# Install required packages
sudo apt install curl wget unzip -y

# Enable BBR congestion control for better performance
echo "net.core.default_qdisc=fq" | sudo tee -a /etc/sysctl.conf

Performance Optimization

BBR Congestion Control

BBR (Bottleneck Bandwidth and RTT) is critical for high-latency connections like China-USA. It can achieve 2700x better throughput than CUBIC in lossy networks.

Impact: BBR dramatically improves performance on connections with packet loss and high latency - exactly what you'll experience with China connections. 
# Check current congestion control
sysctl net.ipv4.tcp_congestion_control

# Enable BBR (requires kernel 4.9+)
echo "net.core.default_qdisc=fq" | sudo tee -a /etc/sysctl.conf
echo "net.ipv4.tcp_congestion_control=bbr" | sudo tee -a /etc/sysctl.conf
sudo sysctl -p

# Verify BBR is active
sysctl net.ipv4.tcp_congestion_control
lsmod | grep bbr

Kernel Network Tuning

# Add to /etc/sysctl.conf
sudo nano /etc/sysctl.conf

# Add these optimizations:
# Increase buffer sizes
net.core.rmem_max = 16777216
net.core.wmem_max = 16777216
net.ipv4.tcp_rmem = 4096 87380 16777216
net.ipv4.tcp_wmem = 4096 65536 16777216

# Enable TCP Fast Open
net.ipv4.tcp_fastopen = 3

# Increase connection backlog
net.core.somaxconn = 1024

# Enable TCP timestamps
net.ipv4.tcp_timestamps = 1

# Enable selective acknowledgments
net.ipv4.tcp_sack = 1

# Apply changes
sudo sysctl -p

Troubleshooting Guide

Common Mistakes to Avoid

Critical Mistakes That Lead to Blocking:

1. Not Installing VPN Before Arrival

Problem: VPN apps and websites are blocked in China.

Solution: Install ALL software, configure servers, and test thoroughly BEFORE traveling to China.

2. Using Wrong Protocols

Problem: Plain WireGuard, OpenVPN without obfuscation detected instantly.

Solution: Always use obfuscated protocols (REALITY, Trojan, Shadowsocks with plugins).

3. Not Keeping Software Updated

Problem: GFW constantly evolves detection methods.

Solution: Update server and client software monthly. Subscribe to project news.

4. Using Datacenter IPs Carelessly

Problem: GFW targets DigitalOcean, Vultr, AWS IP ranges with probabilistic blocking.

Solution: Use multiple servers in different datacenters and rotate when blocked.

5. Not Having Backup Servers

Problem: Single point of failure when server gets blocked.

Solution: Maintain 2-3 servers with different protocols and providers.

6. Ignoring Political Events

Problem: VPN blocking intensifies during sensitive periods (National People's Congress, Tiananmen anniversary, protests).

Solution: Expect connectivity issues during political events. Have multiple backup servers ready.

7. DNS Configuration Errors

Problem: Client uses China DNS servers, revealing browsing activity.

Solution: Force all DNS through VPN. Use DoH (DNS over HTTPS).

8. Enabling Obfuscation Incorrectly

Problem: For NordVPN-style obfuscation, must use OpenVPN (TCP), not NordLynx/WireGuard.

Solution: Read protocol requirements carefully. Test before relying on it.

9. Antivirus Blocking VPN

Problem: Antivirus software blocks VPN as suspicious.

Solution: Add VPN to antivirus exceptions or disable antivirus temporarily.

10. Using WiFi Instead of Cellular

Problem: Hotel/public WiFi has more aggressive filtering.

Solution: Use cellular data when VPN won't connect on WiFi.

Connection Issues

Symptom: Cannot Connect at All

Possible Causes:

  • Server IP blocked by GFW
  • Firewall blocking connections
  • CGNAT preventing port forwarding (home server)
  • Service not running

Diagnostics:

# Check if service is running
sudo systemctl status xray
sudo systemctl status trojan

# Check if port is listening
sudo netstat -tulpn | grep 443

# Check firewall
sudo ufw status

# Test from different network
# Use cellular data instead of WiFi

# Check server from outside China
ping YOUR_SERVER_IP
telnet YOUR_SERVER_IP 443

Symptom: Connects But Very Slow

Possible Causes:

  • GFW QoS throttling (quality of service degradation)
  • Server overloaded
  • Poor routing between China and server
  • BBR not enabled

Solutions:

  • Enable BBR congestion control
  • Try different server location
  • Switch to cellular data
  • Change protocol (e.g., Trojan to REALITY)
  • Use CDN (Cloudflare WebSocket)

Symptom: Works Then Suddenly Stops

Possible Causes:

  • IP address has been identified and blocked
  • Political event causing increased censorship
  • Protocol detected by new GFW update

Solutions:

  • Switch to backup server immediately
  • Change server IP (deploy new VPS)
  • Update to latest protocol version
  • Wait 24-48 hours (some blocks are temporary)

Symptom: Works on Some Apps, Not Others

Possible Causes:

  • App not configured to use proxy
  • App bypassing system proxy settings
  • DNS leak

Solutions:

  • Enable global proxy mode
  • Configure app-specific proxy settings
  • Use transparent proxy on router
  • Check for DNS leaks: https://dnsleaktest.com
